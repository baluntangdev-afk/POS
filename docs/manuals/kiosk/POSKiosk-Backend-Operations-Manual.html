Note  The backend has no screen of its own — it runs quietly as a Windows service and the kiosk app talks to it. This manual explains what it is doing and the few things you may occasionally need to do to it.

1. What the backend is

The “backend” is a small program that runs in the background on the same Windows machine as the kiosk. It is the brain and the filing cabinet of the POS: the kiosk screen only draws pictures and buttons — every product, price, sale, payment, refund and report is created, checked and stored by the backend.

1.1 The three pieces on the machine

PieceWindows service nameJob
Backend servicePOSBackendServiceAnswers the kiosk's requests; enforces the rules; generates receipts and reports.
DatabasePOSPostgresStores the data on disk (PostgreSQL 16).
Kiosk app(not a service)The touch screen staff use.

1.2 Where things live on disk

FolderContents
C:\POSKiosk\The installed programs (kiosk app + backend\ + pgsql\).
C:\posdata\The actual database files. This is what you back up.
C:\POSKiosk\logs\Log files — useful for IT when something goes wrong.
C:\POSKiosk\settings.txtOne line, kiosk.no=<number> — this lane's number, used in every invoice number.
Note  You normally never touch the backend. It starts with Windows and keeps running. This manual covers the occasional times you do: first-day setup, checking it's healthy, backups, and restarting it.

2.2 Other seeded data

The installer optionally seeds sample currencies, tax categories, units of measure, and a starter set of products / modifiers. Tick “Seed initial data” only on the very first install; leave it unticked on upgrades so you don't get duplicates. You can replace the sample products at any time from the kiosk (Inventory → Import CSV).

3. Checking the backend is healthy

3.1 The quick check (any browser on the machine)

Open this addressA healthy system shows
http://localhost:3000/api/v1/healthA page of JSON with "status":"ok" (memory, disk and database all “up”).
http://localhost:3000/api/v1/health/liveok — the service is running.
http://localhost:3000/api/v1/health/readyok — the database is reachable.

If the page won't load at all, the backend service is stopped (Section 7).

3.2 The Windows Services check

  1. Press Win + R, type services.msc, press Enter.
  2. Find POSPostgres and POSBackendService in the list.
  3. Both should say Running and Automatic start-up.

4. The Swagger page — looking inside the backend

The backend publishes a self-documenting web page listing every operation it can perform. You don't need it day to day, but it's the fastest way for a manager or auditor to see what the system does.

  1. On the machine, open http://localhost:3000/api/docs.
  2. You'll see a grouped list (Auth, Users, Products, Sales Orders, Payments, Reports…). Click a group to expand its operations.
  3. Each operation has a plain-English summary, the information it needs, and an example of what it returns.
  4. To actually try one, first get a token: expand Auth → POST /auth/login/email, click Try it out, enter the admin email and password, and Execute. Copy the accessToken from the response.
  5. Click the green Authorize button at the top, paste the token, and close the dialog. Now Try it out works on the other operations.
Note  Treat /api/docs as read-only unless you know what you are doing — some operations change or delete data.

5. What each module does (plain language)

The backend is organised into modules. Here is what each one is responsible for. Most of them are driven entirely from the kiosk screens described in the Kiosk — User Manual.

People & access

ModuleResponsible for
AuthSigning staff in (by email, user ID, or 6-digit PIN), issuing and refreshing security tokens, and the “who am I” check.
UsersThe staff list: create, edit, delete, list “authorizers” (supervisors/admins who can approve voids & refunds), verify a PIN, and the public login roster the kiosk shows.
User Groups / User PermissionsOptional finer-grained permission sets that can be attached to staff.
User Details / User AddressesExtra profile and address information for a staff member.

The menu / catalogue

ModuleResponsible for
Products / Product VariantsEvery sellable item and its size/price variants; CSV import of a whole menu.
Product GroupsCategories that group products, each with an optional cover image.
Modifier GroupsAdd-on and choice lists (sugar level, extra shot) with min/max rules and per-option prices.
CatalogThe fast, read-only feed the kiosk uses to show the menu (active products/categories, with a separate admin feed that also shows hidden items).
Menus / Store MenusThe underlying menu structure and the per-store menu items.
Tax CategoriesVAT / tax rates that can be applied to products.
CurrenciesCurrency definitions (symbol, code).
UOM (Units of Measure)Units such as piece, gram, millilitre — used by inventory.

Stock & recipes

ModuleResponsible for
Materials / Material TypesRaw ingredients and supplies, grouped by type.
Recipes / Recipe ItemsHow much of each material a product consumes when sold.
Inventory StocksCurrent on-hand quantity of each material.
Inventory CountsPhysical stock-take sessions that reconcile the system figure to a real count.

Selling

ModuleResponsible for
POS TerminalsThe identity of each lane (legal name, address, TIN, kiosk number) and its list of payment methods.
Sales OrdersThe order itself: line items, discounts, confirm (complete the sale), void (with supervisor PIN).
PaymentsRecording how an order was paid — cash (with tendered/change), card (reference + last 4), or e-wallet (reference).
RefundsFull or partial refunds against a completed sale, with a reason and supervisor authorisation.
DiscountsThe discount schemes available at checkout (e.g. Senior/PWD, promos).

Reporting

ReportShows
Sales report (overall)Revenue, transaction count and averages for a date range.
Hourly / Daily / MonthlyThe same figures broken down by hour, day, or month.
By Product Group / By ProductRevenue and quantity per category / per item (top sellers).
By UserSales performance per cashier.
By Payment MethodCash vs card vs e-wallet split.
Exportable report / Mark exportedTransactions not yet sent to an external accounting system, and the action to flag them as sent.
Cashier X-ReadingA cashier's running total for today on their terminal (can be read repeatedly; can be “closed” into history).
Cashier Daily ReportThe BIR-style daily summary for a cashier, closable into history.
Z-ReadingThe store-wide end-of-day close, authorised, with a Z counter and sales-by-cashier.

Housekeeping

ModuleResponsible for
Device TransferExport the entire device to one encrypted .posbackup file, or restore one onto a replacement machine (full replace). Admin/Supervisor only.
ERP SyncOptional link to a back-office system: pulls the menu in and pushes orders / reports out on a schedule.
HealthThe status pages in Section 3.
Cron JobsScheduled background tasks — e.g. syncing ERP-managed stock levels every couple of minutes.

6. Routine jobs you may need to do

6.1 Back up the data (do this regularly)

Everything lives in C:\posdata\. Two ways to protect it:

  1. From the kiosk (simplest): Backup & Transfer → Export Backup writes one encrypted .posbackup file. Keep it and its passphrase safe. Do this daily / weekly and before any upgrade.
  2. Database dump (for IT): run pg_dump from C:\POSKiosk\pgsql\bin\ against pos_db on port 5432 and copy the output off the machine.
Important  A backup file contains everyone's PINs (encrypted). Store it like a key list.

6.2 Move to a replacement machine

Use Backup & Transfer on both machines — export on the old one, install the software on the new one, then Import & Restore. Full step-by-step is in the Kiosk — User Manual, “Backup & Transfer”.

6.3 Free up disk space

  • Old log files in C:\POSKiosk\logs\ can be deleted when the system is healthy.
  • Do not delete anything in C:\posdata\.

7. Restarting the backend

A restart fixes many transient problems and is safe — no data is lost. Try the database first if both seem stuck.

7.1 From Windows Services

  1. Open services.msc.
  2. Right-click POSPostgres → Restart. Wait until it says Running.
  3. Right-click POSBackendService → Restart.
  4. Re-check http://localhost:3000/api/v1/health.

7.2 The recovery script

If the services won't come back, run recover-services.bat as administrator from C:\POSKiosk\scripts\. It re-checks the database, re-applies any pending updates and restarts both services.

Note  If problems persist after a restart, collect the newest lines of C:\POSKiosk\logs\backend-error.log and give them to your IT contact.

8. Troubleshooting

SymptomLikely cause & action
Kiosk stuck on “Starting up”Backend or database not running. Restart both services (Section 7); if that fails run the recovery script.
/api/v1/health won't loadPOSBackendService is stopped — start it in services.msc.
Health page shows database “down”POSPostgres is stopped or C:\posdata\ is unreachable. Restart POSPostgres; check the disk isn't full.
“Internal server error” when saving a saleC:\POSKiosk\settings.txt is missing. Re-create it with kiosk.no=<this lane's number> and restart the backend.
Invoice numbers show the wrong lane numberWrong value in settings.txt. Fix it and restart the backend.
Kiosk lists no products after a fresh installInitial data wasn't seeded. Import your menu from the kiosk (Inventory → Import CSV) or re-run the installer's seed step.
Reports are empty for a date you know had salesConfirm the terminal is registered and that the sales were actually confirmed (not left as drafts / voided).
