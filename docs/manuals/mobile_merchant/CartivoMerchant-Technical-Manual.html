1. Overview & tech stack

Cartivo Merchant is a single-screen Flutter Android app that authenticates a device against the Cartivo / DPO backend, opens a WebSocket to the merchant's live order-event stream, and lets an operator patch order status back over REST. There is no user auth, no catalogue, and no reporting — it is a thin real-time client.

Feature-module convention

Feature-first clean architecture. Riverpod notifiers resolve dependencies with getIt<T>() at call time, never via constructor injection. Full rules in lib/features/README.md.

3. Environment (.env) reference

.env is loaded by dotenv.load() at the top of bootstrap() and is declared as an asset in pubspec.yaml. All reads go through EnvConfig; nothing else touches dotenv directly. Every getter has a safe fallback so widget tests run without a file.

WebSocket URL derivation

EnvConfig.wsBaseUrl parses API_BASE_URL, swaps the scheme (http->ws, https->wss), keeps the host, drops the path, and drops the port only when it is the scheme default. OrdersLiveFeedRepository then appends /ws and a ?merchant_id= query param.

API_BASE_URL=https://api.example.com/api/v1
  -> REST : https://api.example.com/api/v1/...
  -> WS   : wss://api.example.com/ws?merchant_id=ABC123

API_BASE_URL=http://192.168.1.34:4000
  -> REST : http://192.168.1.34:4000/...
  -> WS   : ws://192.168.1.34:4000/ws?merchant_id=ABC123
Important  New keys must be added as typed getters on EnvConfig with a fallback — never read dotenv elsewhere.

5. The device authentication chain

Every launch runs a three-call chain before the socket can open. deviceStartupProvider (a FutureProvider) runs it once per launch and memoizes the result; MerchantNotifier.recheckDeviceStatus() refreshes it on demand. All three calls are on MerchantApi.

1 — POST /auth/token

Body{ webhook_secret, merchant_id } (webhook_secret from EnvConfig.webhookSecret)
Accepts200
Returns{ merchant_id, merchant_name, token, exp } — a short-lived webhook JWT scoped to that one merchant
StoredMerchantDeviceStorage.writeToken(token, exp, merchantId) — token, expiry, and the merchant it is scoped to

ensureWebhookToken(merchantId) re-mints when the stored token is missing, within 1 minute of expiry, or tokenMerchantId != merchantId (left over from a previous merchant). This guard is the single source of truth for token freshness — callers must never use storage.token directly.

2 — POST /devices/register

HeadersAuthorization: Bearer <webhook JWT>, Idempotency-Key: <install_id>
BodyRegisterDeviceRequest: platform, install_id, name, app_version, platform_version, device_model, platform_details (android_id, manufacturer, brand, device, sdk_int, is_physical_device)
Accepts200 (idempotent replay) or 202 (fresh enrolment)
Returns{ device_id, status, device_secret?, merchant_id?, merchant_name?, requested_at?, reviewed_at?, review_note? }
device_secretreturned only on 202, once. Persisted then; never overwritten with null on a later 200.

install_id is a v4 UUID generated once (ensureInstallId()) and never cleared, even on a merchant switch — it identifies the install, not the merchant link. status is one of pending / approved / deactivated (rejected is bucketed as deactivated; anything else is unknown). It is cached in secure storage (merchant_device_status) as an optimistic gate read on the next cold start.

3 — POST /devices/token

HeadersAuthorization: Bearer <webhook JWT>
Body{ device_id, device_secret }
Accepts200
Returns{ device_id, merchant_id, token, exp } — a short-lived JWT used as the WS handshake bearer
CachingNot cached across launches. DeviceTokenRepository.mint() is called on every connect attempt. The value is still written to storage (merchant_device_ws_token*) so invalidate() can clear it on a 401/403 handshake rejection.

Approval polling

  • DashboardScreen polls recheckDeviceStatus() every 15 s while the resolved status is non-approved and not tokenUnavailable.
  • It also re-probes on every AppLifecycleState.resumed.
  • On the approved transition the poll stops, any open status dialog is popped, and OrdersFeedNotifier — which watches deviceStartupProvider — reconnects on its own. No restart.

6. The live-orders WebSocket feed

OrdersFeedNotifier (an AsyncNotifier<OrdersFeedState>, kept alive with ref.keepAlive()) owns the socket lifecycle. OrdersLiveFeedRepository is the transport.

Handshake

GET {wsBaseUrl}/ws?merchant_id={merchantId}
Authorization: Bearer {device token from POST /devices/token}
pingInterval: 20s

Connect order mirrors mobile/: ensureWebhookToken -> mint /devices/token -> IOWebSocketChannel.connect -> await channel.ready with a 10 s timeout.

Connection state machine

StateMeaning
connectingInitial attempt in flight
connectedready resolved, subscription live
reconnectingDropped or failed; retry scheduled
disconnectedNo merchant / not approved / deactivated — nothing to connect to

Reconnect / resilience

  • Exponential backoff 1 s -> 30 s (* 2 each try). Reset to 1 s after a connection that stayed up > 5 s.
  • A _connectGeneration counter supersedes stale in-flight attempts so a slow handshake can't clobber a newer one.
  • connectivityStatusProvider transition offline->online triggers an immediate reconnect when the feed is reconnecting/disconnected.
  • 401/403-looking errors call DeviceTokenRepository.invalidate() so the next attempt re-mints.
  • De-dupe: a 200-entry ring of event_ids survives reconnects (the upstream replays a backlog on every resubscribe); only a full _teardown (dispose / merchant change) clears it.
  • Hydration mute: for 4 s after the first successful connect, toasts and OS notifications are suppressed to kill the backlog-replay notification storm.

Wire frame

The WS envelope is { event_id, event_type, data } — no id / received_at / created_at wrapper (those are synthesized). OrderEventDto.fromWireJson returns null (never throws) for: a non-string frame, non-object JSON, an event_type not starting order., a missing event_id, or a non-object data. OrderDataDto.fromWireJson requires only id; every other field is lenient with defaults (the feed mixes full order events with identity-only order.deleted tombstones).

event_typeHandling
order.createdUpsert row, prepend to list, notify
order.updatedUpsert row, replace list entry by data.id, notify
order.cancelledSame as updated; status -> cancelled
order.deletedDelete local row + line items, remove from list

7. REST endpoints

Two calls, both authenticated with the webhook JWT (not the device token). Paths are relative to API_BASE_URL and listed in ApiEndpoints.

GET /merchant/orders

Querymerchant_id
HeaderAuthorization: Bearer <webhook JWT>
ReturnsMerchantOrdersDto — a paginated order-event stream. result.events is already current-state: order.deleted tombstones are applied and unparseable events dropped.
On successOrderEventsDao.replaceAll(merchantId, events) then OrdersState(events)
On failurefall back to dao.getEvents(merchantId); if that is also empty, rethrow (drives the “Couldn't load orders” state); otherwise OrdersState(events: cached, isStale: true) -> the red cached-data banner

PATCH /merchant/orders/{orderId}

Body{ "updates": { "status": "<status>" } } — cancelled included
HeaderAuthorization: Bearer <webhook JWT>
Accepts200
ReturnsOrderStatusUpdateResultDto — echoes the canonical order.updated event the backend also broadcasts on the feed, so the caller converges the list on it
ErrorsDioException is caught and rethrown as a MerchantApiException with a user-facing message (>=500 vs. connection error)

OrdersNotifier keeps a 200-entry _appliedEventIds ring so the socket echo of a change it just made via PATCH is not folded in a second time (which, with an out-of-order echo, could briefly revert the status).

8. Local database & secure storage

Drift database

AppDatabase (@DriftDatabase), one SQLite file mobile_merchant.sqlite in the app documents directory, opened in a background isolate. schemaVersion = 4 with a stepwise onUpgrade.

Accessed only through MerchantDao / OrderEventsDao from the data/ layer — never from domain/. Adding a table: add the Table class, list it in @DriftDatabase, bump schemaVersion, add an onUpgrade branch, re-run codegen.

List-merge rules (subtle, easy to regress)

  • orders_body de-dupes by data.id keeping the highest synthetic id, then sorts desc.
  • mergeLiveOrderEvent drops any existing entry for the same data.id and prepends the incoming event.
  • OrdersNotifier._withStatus rebuilds an OrderEventDto locally only when PATCH succeeds but echoes no usable event.
  • MerchantNotifier.syncOnStartup() only re-emits merchantProvider when the row actually changed — a blind reassignment double-flashes the dashboard spinner.

10. Notifications

OrderNotificationsService (flutter_local_notifications). initialize() runs in bootstrap() before runApp: it sets up the Android channel live_orders (“Live orders”, high importance) and calls requestNotificationsPermission() (Android 13+ runtime prompt). Every call is wrapped in a bare try/catch — a notification failure must never affect the feed.

orderNotificationText(event) is the single source of copy, shared by the OS notification and the in-app toast (showOrderToast via the global appScaffoldMessengerKey) so the two never drift. Notification id is event.eventId.hashCode.

11. Android configuration

Important  The single most important deployment fact. android/app/src/main/AndroidManifest.xml declares only POST_NOTIFICATIONS. The INTERNET permission is present only in the src/debug/AndroidManifest.xml (Flutter adds it there for the dev tooling). A release build therefore ships with no INTERNET permission — and this app is useless without the network. You must add <uses-permission android:name="android.permission.INTERNET"/> to the main manifest before shipping.

Manifest facts

ItemValue
android:labelCartivo Merchant
Launch activity.MainActivity, singleTop, exported
Permissions (main)POST_NOTIFICATIONS only
Permissions (debug overlay)INTERNET
Icon@mipmap/ic_launcher (flutter_launcher_icons, source assets/icon/app_icon.png, min_sdk_android: 21)

Recommended main-manifest additions before release

<uses-permission android:name="android.permission.INTERNET"/>
<uses-permission android:name="android.permission.POST_NOTIFICATIONS"/>
<uses-permission android:name="android.permission.ACCESS_NETWORK_STATE"/>

ACCESS_NETWORK_STATE is pulled in transitively by connectivity_plus but is worth making explicit.

Platform coverage

Android only. There is no ios/, windows/, macos/, or linux/ folder. flutter_launcher_icons is configured with ios: false. The notification service references DarwinInitializationSettings for future parity only.

APK / App Bundle

                              # WEBHOOK_SECRET, CLIENT_ID

Pre-flight checklist

  • INTERNET permission added to the main manifest (see previous section).
  • .env holds the production API_BASE_URL (with https:// so the socket upgrades to wss).
  • WEBHOOK_SECRET and CLIENT_ID are the real integration credentials, not the sample values.
  • ENABLE_LOGGING=false for production.
  • App signing configured in android/app/build.gradle(.kts) (flutter build uses the debug key otherwise).
  • version: in pubspec.yaml bumped (currently 1.0.0+1).
  • Test on a physical device with a real (non-emulator) backend URL — the emulator's 10.0.2.2 fallback masks the INTERNET-permission bug.
Important  .env is bundled into the APK as an asset. Anything in it — including WEBHOOK_SECRET — is extractable from the built APK. Treat the webhook secret as a low-trust integration key, scope it tightly server-side, and rotate it if an APK leaks.

13. Troubleshooting

Socket never reaches “connected”

  • Release build, no orders, pill stuck: missing INTERNET permission. #1 cause. Check the merged manifest in the built APK.
  • disconnected not reconnecting: the guard in build() / checkConnection() found no merchant, no webhook token, or a cached non-approved status. Not a network problem — check deviceStartupProvider.
  • Handshake 401/403: device token rejected — check device_secret is present, the webhook JWT is for the right merchant, and the device is approved server-side.
  • ready times out (10 s): wrong wsBaseUrl (check the [OrdersFeed] handshake — uri: debug line), or the backend has no /ws route on that host.

Enable verbose logging

Set ENABLE_LOGGING=true in .env. LoggingInterceptor then logs every request/response; OrdersFeedNotifier and OrdersLiveFeedRepository emit [OrdersFeed]-prefixed debugPrints (handshake URI, decoded JWT claims, close code/reason, uptime on drop). Filter flutter logs / logcat on OrdersFeed.

Orders load but status changes fail

PATCH uses the webhook JWT via ensureWebhookToken(merchant.merchantId). A 403 “merchant_id does not match” means a stale token scoped to a previous merchant — should self-heal on the next call; if not, clear storage and re-register.

Reset a device completely

  1. Android Settings › Apps › Cartivo Merchant › Storage › Clear storage (wipes secure storage + the SQLite file, including install_id).
  2. Re-open the app; the Register Merchant dialog returns.
  3. Re-register — the backend sees a new install_id, so this enrols as a brand-new device needing fresh approval.

Network retry behaviour

RetryInterceptor retries only pure connection errors / connection timeouts, up to AppConfig.maxNetworkRetries (2). It never retries once the server has responded. Timeouts: connectTimeout 10 s, receiveTimeout 30 s. validateStatus treats anything < 500 as a non-throwing response — MerchantApi._assertSuccess does the real status check.

14. Known constraints & current state

  • Android only. No other platform folders.
  • No user auth. No login screen, no PIN, no per-user audit. The auth feature, route guards, SessionManager and SessionExpiredListener are stubs.
  • One route. '/' -> DashboardScreen. AppRoutes.login is reserved but unwired.
  • Custom-endpoint UI is not surfaced. SettingsService + SETTINGS_PASSWORD support a runtime API_BASE_URL override (custom_api_base_url in secure storage), but the toolbar gear opens MerchantFormDialog, not an endpoint dialog. The override can only be set programmatically / from a future screen.
  • No offline write queue. Status changes and cancellations require a live connection; a failed change is simply lost and must be redone.
  • Single merchant per device. Switching Merchant ID is a destructive re-enrolment.
  • device_secret is single-issue. If secure storage is cleared without a matching server-side device delete, the device row is orphaned — re-register produces a new install_id and a new device.
  • Currency symbol is hard-coded to ₱ in the order card / sheet, regardless of the order's actual currency field (which is used in notification text).

Parity note

Much of this app is a deliberate port of the live-orders subsystem in the sibling mobile/ POS app — the device-status buckets and copy (DeviceStatusVisual), the connect-chain order, the de-dupe ring, and the hydration mute all mirror it. When changing behaviour here, check whether mobile/ needs the same change.
